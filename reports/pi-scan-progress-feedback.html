This report covers the runtime phase protocol and the Progress-tab changes added to Pacsea's Pi-backed AUR scanner. The starting point was a queue of 67 packages paired with the unhelpful message "No active scan."

Conclusion. The scanner now shows a smooth activity marker, exact package identity, current phase, elapsed time, known-work progress, queue order, and pause reasons. It does not invent a percentage for model execution.

Confidence: 96/100. Formatting, strict Clippy, compilation, the full serial test suite, focused runtime tests, and TUI rendering tests pass. A live paid-provider scan and recorded terminal animation were not run.

How progress reaches the screen

The durable queue remains the source of truth for queued, active, and terminal work. The new phase state is process-local. This matters because a recovered scan can prove that work was interrupted, but it cannot honestly recover the last transient step shown before shutdown.

Preparation

Preparing and resolving metadata

The scanner registers the exact item and retrieves the AUR metadata needed for immutable acquisition.

Network recovery

Waiting for the bounded retry

A transient pre-model failure shows a retry wait instead of appearing frozen. The existing one-minute, cancellation-aware retry policy is unchanged.

Evidence

Acquiring recipe and source snapshots

The phase starts before bounded acquisition and integrity checks. It does not claim completeness before those checks finish.

Model

Running Pi and validating its response

The selected model call and typed response validation are one observable blocking operation, so the UI labels them together.

Identity

Rechecking mutable inputs and AUR HEAD

The scanner reports the post-analysis identity check before accepting a result.

Completion

Validating and finalizing

The last phases cover frozen-target validation, result storage, accounting, and durable completion.

What the user sees

  1. At a glance

    A fixed-width bar shows completed terminal items over all known terminal, running, and queued items. Labels break out running, queued, completed, failed, cancelled, and interrupted counts.

  2. During a scan

    The active block shows the package base, immutable commit, correlation ID, animated current step, elapsed time, and reservation ceiling. A missing or stale phase falls back to "Scan in progress" rather than guessing.

  3. While queued

    An eligible queue uses the animated waiting marker. A paused queue uses a static pause marker and names every active pause reason. Queue entries are numbered so sequential order is visible.

  4. After a terminal outcome

    Completion, failure, cancellation, and interruption update the summary with the exact projected status. A failure still keeps its actionable reason.

Limits and rollout guidance

Not live-tested

Provider timing

Deterministic tests cover phase ordering and rendering, but no paid provider call was made. Very short validation and finalization phases may pass between redraws. The scanner never delays work to keep a label visible.

Terminal font

Glyph support

Braille and pause glyph appearance depends on the terminal font. Explicit text carries the same state if a glyph renders poorly.

Failure fallback

No invented terminal count

If the production owner cannot retrieve an exact durable terminal record after an error, Pacsea shows the error reason but does not fabricate a failed count.

Rollback

No migration needed

The phase state is transient. Reverting the protocol and Progress-tab changes requires no persistent state migration or cleanup.

Recommended manual check. Rebuild Pacsea, start a small foreground Pi Scan, and watch the Progress tab move through metadata, acquisition, model execution, identity recheck, and finalization. Also pause a queued scan and confirm that the marker becomes static.
