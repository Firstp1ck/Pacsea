Architecture and trust flow

The setup controller is always available, even when production scanning is disabled. Wizard state owns only a draft. Probe and candidate validation are write-free. Only a correlated Apply can create a queue-inert candidate, persist consent/settings, and request central ownership transfer.

Isolation

Draft boundary

Candidate settings, route facts, confirmations, correlation, and apply status stay in PiScanSetupWizardState. Cancel drops the draft and sends no runtime request.

Probe boundary

No model call

The adapter issues only get_available_models, get_commands, and get_state. CLI and RPC processes have deadlines and process-group cleanup.

Consent boundary

Two durable projections

Runtime consent covers observation and foreground payment. Setup consent separately carries background payment, disclosure, fallback, readiness, Pi version, and pricing binding.

Ownership boundary

One active owner

Central integration stops the old owner before activation and installs all channel endpoints together. Uncertain shutdown never triggers a duplicate-owner restore.

Wizard decisions

  1. Welcome: advisory scope, data flow, no package execution, Pi-owned credentials.
  2. Pi readiness: binary resolution, supported version, required flags and isolated tool contract.
  3. Route: exact advertised provider/model and thinking level.
  4. Pricing/privacy: per-route worst-case reservation, provenance/freshness, disclosure, foreground payment, readiness warning.
  5. Optional behavior: observation, paid background work, exact fallback, budgets, retention, credential-free HTTPS proxy.
  6. Review: every effective value, compiled maxima, six decisions, exact binding and transaction effects.
  7. Activate: re-probe, persist, stop old owner, activate, restore consent, or show retryable failure.
Crash ordering: two separate files cannot share one filesystem rename. The implementation writes private consent first and settings second. A process/power interruption between them therefore leaves the prior settings authoritative; the mismatched consent fails closed. In-process failures restore both snapshots, and rename durability includes parent-directory fsync.

How to use the completed flow

  1. From Search, press the configured Pi Scan shortcut (default Shift+A). Incomplete setup opens Welcome even when pi_scan_enabled = false.
  2. Verify Pi, select an exact route, review pricing/privacy, choose conservative optional behavior, then inspect the complete Review page.
  3. Press a on Review to Apply. Success transitions to production in the same process; no manual settings edit or Pacsea restart is required.
  4. Later, press r on advanced Setup or Ctrl+G on a Pi Scan Config Editor row to rerun guided setup. Material expert edits invalidate prior setup consent.

Residual risks and limitations
  • The host Pi binary remains an accepted optional-dependency trust boundary; Pacsea constrains argv, environment, tools, lifecycle, output, and authority but does not claim an OS sandbox.
  • No paid provider/model request was made during setup validation. Live evidence covers metadata and runtime activation, not provider billing behavior.
  • A literal power-cut test between consent and settings replacement was not run. The ordering is designed so prior settings remain authoritative, while in-process after-consent failure and rollback are deterministic tests.
  • German and Hungarian key completeness and placeholder policy are tested, but translation quality was not reviewed by native speakers.
  • Responsive rendering is automated; no formal interactive terminal usability study was performed.
